## 三、工作过程（SPI）

1. ESP32 初始化摄像头（OV2640 请求 240×240 RGB565；OV5640 退回 800×600 后裁剪缩放），摄像头脚位与原工程完全一致。
2. ESP32 先把这一行拼成 485 字节的包：`A5 5A | 帧号 | 行号 | 异或 | 480 字节 RGB565`。
3. STM32 把 SPI2 的 RX DMA 武装成 485 字节，**然后**把 PB10(READY) 拉高。
4. ESP32 等 READY=1 → CS(GPIO43) 拉低 → SCK(GPIO45)/MOSI(GPIO44) 送出 485 字节 → CS 拉高。
5. STM32 的 DMA 收满立刻把 PB10 拉低（表示这一包接住了），再校验 magic / 整包异或 / 行号。
6. 校验通过就用硬件 SPI1 把 480 字节 RGB565 写到 ILI9341 对应行（240×240 居中，Y 起点 40）；行号 0 开始新的一帧。
7. 回到第 3 步，重复到 240 行全部显示。

> 为什么接收必须用 DMA：SPI 从机没有流控，8MHz 下 1 个字节只有 1µs，而写一行屏要 200µs 以上。
> 边收边写必然 OVR 丢数据——这正是上一版 SPI 一包都收不到的根本原因。

## 四、排错速查

- **屏幕只显示蓝色 + 顶栏计数**：正常，说明程序在跑。看顶栏 `V7` 确认是 SPI 版（`V6` 是旧 UART 版，必须重烧）。
- **连 `V7` 都没有 / 全屏蓝**：屏本身没起来。查 PA0/PA1/PA2/PA5/PA7 与背光 PA4；或把 `LCD_SPI_BR` 从 `0x01` 改成 `0x02`（18MHz → 9MHz）。
- **`T` 持续增长、`K` 不动**：STM32 没收到 SPI 数据。依次查 ① STM32 是否已烧 V7；② GPIO43/44/45 ↔ PB12/13/15 是否接对（**SCK 和 MOSI 接反最常见**）；③ 有没有共地。
- **`G` 增长**：magic 错，字节错位。通常是线太长/时钟太快，两端把 `LINK_SPI_HZ` 改成 `4000000UL` 重编重烧。
- **`C` 增长**：异或校验错，同样是高速误码，处理同上；也可能是没共地或杜邦线接触不良。
- **`W` 增长**：行号错，中间丢了一包；程序会丢弃残帧并从行 0 重新对齐。
- **`L` 不动但 `T` 也不动**：主循环卡住，检查是否进入了某个死循环。
- **画面花屏/斜条纹**：屏 SPI 太快（`LCD_SPI_BR` → `0x02`）或链路误码（`LINK_SPI_HZ` → `4000000UL`）。
- **颜色红蓝反了**：把 `camera_preview.h` 里的 `CAM_SWAP_RGB565` 改成 0，两端重新编译烧录。
- **文字/画面上下颠倒**：调整 `ili9341.h` 里的 `LCD_MADCTL_VALUE`（当前 `0x48`）。
- **摄像头初始化失败**：先确认 OV2640 的 `PID=0x26` 日志；再查 3.3V 电流和 16 根 DVP 线。
